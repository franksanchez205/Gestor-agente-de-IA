1. Qué es Spec Driven Development
Spec Driven Development (SDD) significa: primero escribimos qué queremos, después
cómo lo haremos, y recién al final escribimos código. Todo queda en archivos Markdown
dentro del repo.
Es especialmente útil cuando trabajamos con agentes de IA (Claude Code, Copilot,
Cursor, Codex). El agente no recuerda conversaciones anteriores, pero sí puede leer
archivos. Si la intención está escrita, el agente (y cualquier persona nueva en el equipo)
entiende el proyecto sin preguntar.
Idea clave para los alumnos: el prompt se pierde, la spec se queda.
2. Spec, plan y task
Son tres niveles de detalle de una misma cosa. Van siempre en este orden y cada uno se
apoya en el anterior.

Spec
Describe el comportamiento desde el punto de vista del usuario. No habla de tecnología.
Tiene tres partes mínimas: objetivo, historias de usuario y criterios de aceptación. Si una
frase menciona Express o Angular, probablemente pertenece al plan.
Plan
Traduce la spec a decisiones técnicas: archivos, endpoints, tablas, componentes. Aquí sí
hablamos de stack. La persona lo revisa antes de que el agente toque código.
Task
Un paso pequeño, verificable y que se puede marcar como hecho. Regla práctica: una task
se termina en una sola sesión del agente y se puede comprobar en menos de 2 minutos.
Toda task que agrega código incluye sus pruebas unitarias.
El ciclo
1. Escribir la spec y aprobarla.
2. Pedir al agente el plan y revisarlo.
3. Pedir al agente las tasks.
4. Ejecutar las tasks una a una, marcando [x] .
5. Verificar los criterios de aceptación de la spec.
Si algo cambia a mitad de camino, se corrige primero la spec, después el código.

AGENTS.md
Es el "README para agentes". Un archivo en la raíz que la mayoría de herramientas leen
automáticamente al empezar (Claude Code usa CLAUDE.md ; se puede crear un
CLAUDE.md  que solo diga @AGENTS.md ). Contiene:
Qué es el proyecto en una línea.
Dónde está la documentación.
Comandos para instalar, ejecutar y probar.
Reglas del equipo ("no instales librerías sin preguntar").
El flujo de trabajo: spec → plan → tasks.
Debe ser corto. Si crece, el detalle se mueve a docs/  y AGENTS.md solo enlaza.
La carpeta docs
product.md : el problema, el usuario, qué entra y qué no.
tech-stack.md : lenguajes, frameworks, base de datos, versiones.

4. Práctica: AGENTS.md y docs (pasos 1 y 2)
Vamos a construir TodoLite: una lista de tareas con backend Express (datos en memoria)
y frontend Angular. Duración sugerida: 20 minutos para estos dos pasos. Todo se escribe a
mano, muy básico; la gracia es que exista, no que sea perfecto.
Paso 1: crear el repo vacío
mkdir todolite && cd todolite
git init
mkdir -p docs/specs
touch AGENTS.md docs/product.md docs/tech-stack.md docs/architecture.md
Todavía no creamos backend/  ni frontend/ . Eso lo hará la spec 000.
Paso 2: llenar los archivos (versión mínima)
AGENTS.md
# AGENTS.md
TodoLite: app web para gestionar una lista de tareas personales.
## Documentación
- Producto: docs/product.md
- Stack: docs/tech-stack.md
- Arquitectura: docs/architecture.md
- Specs: docs/specs/NNN-nombre/
## Flujo de trabajo
1. No escribas código sin una spec aprobada.
2. Antes de programar, escribe plan.md (con su sección de Pruebas) y tasks.md 
en la carpeta de la spec.
3. Haz una task a la vez, con sus pruebas, y márcala con [x] solo si las 
pruebas pasan.

spec.md
# 001 - CRUD de tareas
## Objetivo
Poder gestionar una lista de tareas mientras la app está en uso.
## Historias
- Como usuario, quiero agregar una tarea escribiendo su título.
- Como usuario, quiero ver todas mis tareas.
- Como usuario, quiero marcar una tarea como hecha.
- Como usuario, quiero borrar una tarea.
## Criterios de aceptación
- [ ] Al escribir un título y pulsar "Agregar", la tarea aparece en la lista.
- [ ] No se puede agregar una tarea con título vacío.
- [ ] Al marcar el checkbox, la tarea se ve tachada.
- [ ] Al pulsar "Borrar", la tarea desaparece.
- [ ] Al recargar la página, las tareas siguen ahí (mientras el backend siga 
encendido).
- [ ] Hay pruebas unitarias para crear, listar, completar, borrar y para el 
título vacío, y todas pasan.
## Fuera de alcance
- Editar el título, ordenar, filtrar.
- Guardar las tareas entre reinicios del backend (no hay base de datos).

- GET    /api/tasks        → lista todas
- POST   /api/tasks        → { title } → 400 si está vacío
- PATCH  /api/tasks/:id    → { done } → 404 si no existe
- DELETE /api/tasks/:id    → 404 si no existe
## Frontend
- task.service.ts con los 4 métodos HTTP.
- AppComponent: input + botón Agregar, lista con checkbox y botón Borrar.
## Pruebas
- Backend, store (test/store.test.js): cada función de store.js, con reset() 
antes de cada prueba.
- Backend, API (test/tasks.test.js, supertest):
  - POST crea una tarea; POST con título vacío → 400
  - GET devuelve las tareas creadas
  - PATCH cambia done; DELETE la elimina; id inexistente → 404
- Frontend:
  - task.service.spec.ts: cada método usa la URL y el verbo correctos
  - app.spec.ts: con el input vacío, Agregar no llama al servicio
